# NH3 Vue 3 工程规则

## 作用范围

仅将此 skill 用于 Vue 3 前端项目，尤其是 Vue 3 + Vite + TypeScript 应用、SPA 后台系统、仪表盘、工具型界面和 Vue 组件库工作。若目标仓库不是 Vue 3 项目，应说明该 skill 超出支持范围，并只使用常规工程判断继续处理。

不要将这些指令视为 React、Svelte、Angular、Nuxt、Next、SvelteKit 或非前端项目的指导。其他技术栈可能共享部分相近工程关注点，但此 skill 不保证在 Vue 3 以外取得良好效果。

## 核心原则

1. 应用此 skill 前先确认目标是 Vue 3。检查 `package.json`、Vite 配置、router/store 设置、SFC 使用方式和组件库约定。
2. 编辑前先检查目标项目。路由、导航、权限、文案、API、状态、布局、测试和构建配置共同定义真实工程边界。
3. 保留已有能力。导航清理、页面合并或重构不得让功能变得不可达。
4. 保持改动窄。不要无必要地格式化无关文件、重写无关模块或替换依赖。
5. 操作型页面应紧凑、清晰、可扫描。构建可用工具，而不是营销页面。
6. 每个新增抽象、规则或文件都必须提供具体价值。
7. 最终输出必须说明改动文件、静态检查和未执行的验证。

## 项目结构

典型 Vue 3 SPA、后台、仪表盘和组件库项目可使用此结构。若仓库已有结构，应遵循现有结构并保持相同职责边界。

```text
project/
├── docs/                    # 项目规则、架构说明、发布说明
├── public/                  # 公开静态资源
├── src/
│   ├── api/                 # API 客户端、请求适配器、DTO 边界
│   ├── assets/              # 源码管理的图片、字体、图标
│   ├── components/          # 可复用 UI 和业务组件
│   ├── composables/         # Vue composables 和生命周期相关复用逻辑
│   ├── config/              # 环境和运行时配置映射
│   ├── constants/           # 常量、枚举、稳定映射
│   ├── directives/          # Vue 指令
│   ├── i18n/                # 本地化和用户可见文案
│   ├── layouts/             # 应用外壳和布局框架
│   ├── pages/               # 按业务域分组的路由页面
│   ├── router/              # 路由、守卫、路由元信息
│   ├── stores/              # 全局状态和跨页面派生状态
│   ├── styles/              # 全局样式、tokens、resets
│   ├── theme/               # 主题 tokens 和组件库覆盖
│   ├── types/               # 共享类型
│   └── utils/               # 不耦合 UI 的纯工具
├── tests/                   # 单元、集成和端到端测试
├── package.json
└── README.md
```

## 默认禁止项

| 禁止项 | 约束 |
|---|---|
| 随意删除功能页、路由或菜单项 | 确认没有需求依赖它们，或保留清晰的替代入口 |
| 随意改动鉴权、支付、导入/导出、权限或其他敏感流程 | 仅在明确要求或修复明确缺陷时触碰 |
| 硬编码用户可见文案 | 使用 i18n 或仓库既有文案系统 |
| 创建分散的规则文件 | 集中规则，避免未来 AI 误读 |
| 增加不必要依赖 | 先检查现有框架、组件库和工具 |
| 使用 Tailwind CSS 或其实用优先的风格模式 | 使用语义化 CSS、组件 scoped `<style>` 或项目已有设计系统代替 |
| 过度抽象 | 不为小功能创建大量函数、组件、composables 或 stores |
| 格式化无关文件 | 保持 diff 窄且可审查 |
| 回滚工作区已有改动 | 除非明确要求，否则视为他人的工作 |
| 用长文案解释未完成 UI | 完成它、禁用它，或移除入口 |

## UI 和信息架构

1. 后台、仪表盘和工具页应紧凑、克制、可扫描。
2. 首屏应呈现真实控件、数据、任务状态、表单、筛选或主要操作。
3. 避免 hero 区、营销渐变、口号、装饰性指标和无意义说明侧栏。
4. 仅在必要分组、重复对象或弹窗内容中使用卡片。
5. 文案应简短，并解释状态、结果或下一步动作。
6. 桌面和窄屏布局必须避免文本溢出、控件重叠、按钮裁切和不可用导航。
7. 仅当多个页面代表同一对象或工作流的不同视图时才合并页面。
8. 删除路由或菜单前，检查入口、链接、权限、测试、文档和既往需求。
9. 迁移后的功能需要清晰替代路径；可行时保留 deep link 或重定向。
10. 成熟工作流应进行连接修复和视觉收敛，而不是任意重设计交互。

### 页面内部布局

1. 围绕稳定工作区构建操作型应用：导航、可选列表/筛选面板，以及可伸缩主内容面板。
2. 导航和次级面板应有明确最小/最大宽度。主面板设置 `min-width: 0` 并吸收剩余空间。
3. 页面标题、筛选、tabs 和操作使用一致的横向栏。控件对齐到共同高度和基线，不要把每个动作放进独立卡片。
4. 当工作流需要保留上下文时，让长导航、列表和详情内容独立滚动。没有清晰归属边界时避免嵌套滚动区。
5. 使用 8px 间距节奏，常用 4、8、12、16、24px。更大间距仅保留给主要页面区域。
6. 窄屏下将次级面板折叠为抽屉、覆盖层或明确视图切换。保持主任务和主操作可达。

### 视觉系统

1. 为页面背景、抬升表面、导航表面、边框、主强调色、弱化文本、成功、警告和错误状态定义语义 tokens。
2. 默认使用中性表面和细 1px 分隔线构建结构。主色用于选中、焦点、链接和关键操作，而不是给每个表面染色。
3. 保持圆角一致，控件、列表项、popovers 和框定内容通常使用 6-8px。避免过多胶囊形状和大圆角悬浮卡片。
4. 谨慎使用阴影，用于说明 hover、选中、popovers 和临时抬升。大部分层级应由边框和背景对比承担。
5. 建立紧凑字号层级：页面/详情标题约 18-24px，条目标题约 15-17px，正文约 14-16px，元信息约 12-13px。已有字号系统时匹配仓库。
6. 熟悉操作使用图标，不熟悉图标配 tooltip。图标按钮保持正方形和尺寸稳定。
7. 不依赖单一色相。使用中性基础、一个主强调色和有区分度的语义色，并保证可访问对比度。

### 列表、详情和状态

1. 列表项应呈现清晰顺序：标题、短元信息、简短描述、可选标签、时间戳或状态。先截断次要文本，不让控件位移。
2. 选中项使用克制的边框、背景和文字颜色组合区分。Hover 可使用 1-2px 轻微抬升或小阴影，但不得移动周围布局。
3. 详情视图应在紧凑头部保留身份和操作，下方保持内容可读，长内容由自身滚动区域承载。
4. 标签保持小且次要。用它们表达分类或状态，不作为主要视觉结构。
5. 将 loading、空状态、错误和数据过期状态放在它们影响的面板内。保留周围导航和恢复操作。

### 动效和数据绘制

1. Hover、focus、选中、面板进入和小状态变化使用 150-250ms 过渡。尊重 reduced-motion 偏好，避免持续装饰动画。
2. 点击反馈限制在局部，可使用缩放、颜色或受控 ripple。除非工作流需要，不动画改变宽、高或相邻布局。
3. 图表、关系图、canvas 和节点图必须使用稳定尺寸、可读标签、一致的 1-2px 线条、克制填充和语义化颜色映射。
4. 优先使用直接标签、对齐图例、清晰选中、缩放限制和有用空/加载状态，而不是装饰效果。
5. 仅在能说明深度或品牌语境时使用渐变、发光、模糊和玻璃效果。它们不得降低对比度或成为页面主要视觉语言。

## i18n 和文案

1. 新增或修改的用户可见文本必须使用仓库的 i18n/文案系统。
2. Locale keys 必须在受支持语言间保持对齐。
3. 菜单、按钮、对话框、空状态、校验和错误必须匹配真实行为。
4. 空状态应简短并面向行动。
5. 不要添加解释明显 UI 结构、设计意图或策略的文案。
6. 内部日志、测试描述和开发者注释在非用户可见时不需要 i18n。

## JavaScript 和 TypeScript

1. 禁止使用 `var`。只使用 `const` 或 `let`。
2. 默认使用 ES6+ 语法：modules、箭头函数、解构、模板字符串、可选链和空值合并等。
3. 优先使用 `const`；仅在需要重新赋值时使用 `let`。
4. 不要引入隐式全局、隐式 `any` 或无类型对象透传。
5. 显式建模 API DTO、领域对象、组件 props、路由元信息和 store state。
6. 不要用 `any` 绕过类型问题；如果不可避免，将其局部隔离并说明原因。
7. 异步逻辑必须处理失败状态。
8. 公共导出必须有清晰边界，不随意暴露内部实现细节。

## 函数和抽象边界

小功能不应拆分成过多函数。函数定义必须服务语义边界、复用、可测试性、副作用隔离或复杂度降低。

### 何时抽函数

| 场景 | 要求 |
|---|---|
| 逻辑被复用 | 至少两个真实调用点，或一个稳定共享能力 |
| 分支复杂 | 抽取让主流程更易读 |
| 业务含义稳定 | 函数名清楚表达领域意图 |
| 逻辑需要直接测试 | 解析、转换、校验和纯逻辑适合抽取 |
| 副作用需要隔离 | 网络、存储、路由、埋点等效果需要清晰边界 |

### 何时不要抽函数

| 反模式 | 原因 |
|---|---|
| 包装单行代码 | 只增加跳转成本 |
| 给每个小按钮创建一个薄处理器 | 内联或合并成清晰处理器 |
| 把小流程拆成泛化步骤 | 制造膨胀并隐藏意图 |
| 只是为了让代码看起来有结构而抽取 | 损害局部可读性 |
| 使用模糊命名 | `handleProcess`、`doAction` 和 `manageData` 隐藏含义 |

## 组件、状态和模块

1. 仅为真实复用、复杂度降低或稳定业务片段抽取组件。
2. 页面组件负责编排；业务组件拥有可复用领域 UI；基础组件拥有基础 UI。
3. 不为一个页面局部的小片段创建许多文件。
4. 跨页面状态属于 stores；页面局部状态留在本地。
5. 纯 helpers 放在 `utils`；与生命周期/UI 相关的逻辑放在 composables。
6. API clients 处理请求、响应和类型边界，不处理页面状态。
7. 配置映射放在 `config`，不要散落在页面中。

## 注释标准

函数、变量和工具类文件头必须有注释。其他位置的注释不强制，仅在有助于说明目的、业务含义、约束或非显而易见行为时添加。

强制要求：

1. 每个新增或修改的函数或方法都必须添加清晰注释，包括 composable、生命周期回调、事件处理器和工具函数。说明其用途，并在相关时说明输入、输出、副作用、约束或重要行为。
2. 每个新增或修改的变量或常量都必须添加紧邻注释，包括响应式状态、ref、计算值、store 字段和模块级常量。说明该值代表什么或为何存在。
3. 每个新增或修改的工具类或工具/辅助文件都必须添加文件头注释，包括 `utils` 下的文件、共享 helper 模块和工具脚本。说明文件职责和边界。
4. import、类型、模板区域、控制流分支、样式、配置项和测试的注释均为可选，除非需要解释非显而易见的行为。

每一条新增或更新的注释都必须根据目标项目、文件或模块中当前作者已经形成的使用语言来选择。此语言选择要求是强制规则，绝不能忽略。若当前作者持续使用中文注释，使用简洁中文。若当前作者持续使用英文注释，使用简洁英文。若周围代码混合，匹配最近的稳定约定，并避免在同一条注释中混用语言。

### 工具文件头示例

```ts
/**
 * 导航选中态和路由映射的菜单状态解析。
 *
 * 本模块将路由路径映射到稳定菜单 key。它不拥有页面级交互状态。
 */
```

### 函数注释示例

```ts
/**
 * 解析当前路由的菜单 key。
 *
 * 详情路由和列表路由可能共享父入口，因此精确匹配优先于前缀匹配。
 */
export function resolveActiveMenuKey(pathname: string): string { ... }
```

### 变量注释示例

```ts
// 当前路由没有明确导航映射时使用的稳定菜单 key。
const fallbackMenuKey = 'overview'
```

### 多行注释格式

`/** */` 风格的多行注释必须至少占三行。不得压缩为单行。

```ts
/**
 * 解析当前路由的菜单 key。
 */
```

```ts
/** 解析当前路由的菜单 key。 */
```

### 注释禁止项

| 禁止 | 原因 |
|---|---|
| 新增或修改的函数、变量或工具文件头缺少注释 | 这些位置的注释是强制要求 |
| 仅复述语法的注释 | 没有解释目的、含义、约束或行为 |
| 装饰性分隔块 | 降低扫描效率 |
| 在同一条正文注释中混用语言 | 使协作和维护不一致 |
| 用注释解释未完成 UI | UI 应完成、禁用或移除 |
| 过期注释 | 更新或删除；强制注释必须替换为最新说明 |

TODO/FIXME/HACK 必须包含范围和下一步动作：

```ts
// TODO(接口联调): 状态枚举确认后移除兼容映射。
// FIXME(导航): 窄屏折叠时保持用户区域稳定。
```

## 环境策略

开发、测试、预发和生产必须分离。仅使用必要配置，不要过度区分，文件名因框架而异；Vite 类项目可使用：

```text
.env.example              # 公开模板，提交
.env.local                # 本地 secrets 和开发者覆盖，忽略
.env.development          # 开发默认值，若提交则不含 secret
.env.test                 # 测试默认值，若提交则不含 secret
.env.staging              # 预发默认值，若提交则不含 secret
.env.production           # 生产默认值，若提交则不含 secret
```

### 环境变量规则

| 规则 | 要求 |
|---|---|
| 浏览器暴露 | 使用框架公共前缀，如 `VITE_` |
| Secrets | 不得暴露到浏览器 bundle 或公开前端配置 |
| 文档 | 在 `.env.example` 或 docs 中记录支持的变量 |
| 校验 | 尽可能在启动/构建前校验必需变量 |
| 分离 | 生产不得静默回退到开发端点 |
| 可追踪 | 生产构建可包含非敏感 commit/build 元数据 |

## 开发环境

1. README 或 docs 必须说明包管理器、安装命令、启动命令和必需环境变量。
2. `dev` 应能在没有生产凭据的情况下启动本地开发。
3. 本地调试配置不得泄漏进生产配置。
4. Typecheck、静态检查、单元测试和 e2e 测试应可独立运行。
5. 开发日志可以详细；面向用户的调试 UI 必须隐藏或受开关保护。
6. 不要把本地绝对路径写入源码、配置模板或文档示例。

建议 Vue 3 scripts：

```json
{
  "scripts": {
    "dev": "vite",
    "typecheck": "vue-tsc --noEmit",
    "lint": "eslint .",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:e2e": "playwright test",
    "build": "npm run typecheck && vite build",
    "preview": "vite preview"
  }
}
```

Vue 3 类型检查优先使用 `vue-tsc --noEmit`。当仓库已有不同包管理器和脚本名时，使用仓库既有约定。

## 依赖版本

在 Vue 3 项目中新增或更新依赖时，优先使用较新的稳定版本。避免使用已被生态淘汰的旧版本。

常见 Vue 3 项目依赖参考版本：

| 包 | 建议版本 |
|---|---|
| vue | ^3.5.0 |
| vue-router | ^4.5.0 |
| pinia | ^2.2.0 |
| axios | ^1.7.0 |
| echarts | ^5.5.0 |
| dayjs | ^1.11.0 |
| @vitejs/plugin-vue | ^5.2.0 |
| vite | ^5.4.0 |
| typescript | ^5.7.0 |
| vue-tsc | ^2.2.0 |
| less | ^4.2.0 |
| sass | ^1.80.0 |
| unplugin-vue-components | ^0.28.0 |
| unplugin-auto-import | ^0.19.0 |
| vite-plugin-compression | ^0.5.0 |
| @types/node | ^22.0.0 |

规则：

| 规则 | 要求 |
|---|---|
| 保持较新 | 以上表版本为最低版本；更新的稳定版本优先使用 |
| 检查既有 | 当仓库已有较新大版本时匹配仓库版本 |
| 避免过旧 | 新建 Vue 3 项目时不安装 Vue 2.x、Vue Router 3.x、Vite 2.x 等已结束生命周期的大版本 |
| Lockfile | 使用仓库 lockfile 和对应包管理器进行确定性安装 |

## 生产环境

生产必须稳定、可追踪且安全。

| 方面 | 要求 |
|---|---|
| 类型检查 | 生产构建必须可通过类型检查 |
| 环境 | API endpoint、base path 和 asset path 必须明确 |
| Source maps | 根据部署上下文明确开启、关闭或保护访问 |
| Bundle | 添加大依赖时评估体积影响 |
| Assets | 使用利于缓存的文件名和正确 public base path |
| Errors | 关键应用应有错误边界或错误上报 |
| Feature flags | 未完成功能默认禁用 |
| Debugging | 不向最终用户暴露 debug 面板、测试入口、内部链接或 stack traces |

运行时规则：

1. 不依赖 dev-server 行为。
2. SPA 托管需要路由 fallback。
3. 受保护路由必须 fail closed。
4. 用户可见错误页应简短、清晰、可行动。
5. 构建元数据可用于排障，但不得包含 secrets 或内部敏感路径。
6. 发布前必须知道回滚路径。

## 测试和验证策略

默认不主动运行构建、启动服务或执行运行时验证。仅当请求明确要求验证、运行、构建、测试、打开浏览器或启动服务时，才运行这些命令。否则只执行静态检查：语法、参数、路径、配置字段、imports/exports 和引用一致性。

### 默认静态检查

| 项目 | 检查 |
|---|---|
| Markdown / YAML | Frontmatter、标题、链接和格式合理 |
| package scripts | 命令名、参数和依赖引用可信 |
| TypeScript 示例 | 语法、泛型、imports/exports 和 ES6+ 用法合理 |
| 环境变量 | 名称、前缀、用途和敏感性合理 |
| 路由/导航建议 | 路径、入口和权限关系自洽 |
| 配置示例 | 字段名、嵌套和默认值清晰 |

### 明确要求验证时

| 请求 | 动作 |
|---|---|
| Build | 运行项目构建命令 |
| Test | 运行相关测试 |
| Typecheck | 运行 `vue-tsc --noEmit` 或项目既有 Vue typecheck 命令 |
| Browser validation | 启动本地服务并交互检查受影响页面 |
| Pre-release check | 根据项目能力运行 build、tests、preview 或 staging smoke test |

如果命令无法运行，说明原因和未验证范围。

## 构建和 CI

Vue 3 项目应有可组合的质量门槛。除非明确要求，不要运行构建、测试或服务启动命令。

```text
install
-> lint / format check
-> typecheck
-> unit tests
-> integration or e2e tests
-> production build
-> preview or deploy smoke test
```

CI 规则：

| 规则 | 要求 |
|---|---|
| 确定性安装 | 使用 lockfile 和配置好的包管理器 |
| Secret 安全 | CI 日志不得打印 secrets |
| 环境分离 | Staging 和 production 使用不同配置 |
| Artifacts | Build artifacts 仅进入配置好的输出目录 |
| Failures | 失败测试不能无说明地标记为可接受 |
| Cache | 依赖/构建缓存必须可复现且可失效 |

## 安全和可靠性

| 方面 | 规则 |
|---|---|
| Auth | 真实授权不能只依赖前端检查 |
| XSS | 避免 raw HTML；sanitize 富文本渲染 |
| Upload/import | 校验类型、大小、进度、错误和取消状态 |
| API errors | 规范化预期错误，并显示简短 UI 反馈 |
| Storage | 不要将 secrets 存入 localStorage/sessionStorage |
| Dependencies | 添加大型或高风险包前先评估 |
| Accessibility | 控件需要名称、焦点态、键盘可达和合理对比度 |
| Performance | 避免不必要的整页重渲染、巨大 bundles 和阻塞首屏 |

## 协作规则

1. 编辑相关代码前使用 `rg` 等快速搜索工具。
2. 将已有脏工作区改动视为他人的工作；不要回滚。
3. 较大任务在修改文件前说明编辑范围。
4. 优先使用 patch 编辑；若工具失败，使用安全 UTF-8 写入并保持 diff 窄。
5. 未经明确要求，不创建多个规则文件。
6. 用户要求实现时，不停留在计划。
7. Review 请求先给出发现，并附文件/行号。
8. 最终回复保持简洁：改动文件、静态检查和未执行验证。

## Vue 3 范围

仅适用于 Vue 3 前端应用：

- Vue 3 + Vite：遵循 SFC、Composition API、composables、Vue Router、Pinia 或既有状态方案。
- Vue 组件库：自定义基础控件前优先使用既有组件库。
- 当仓库已使用 Vue Options API 时可以维护它，但新增代码应遵循本地 Vue 3 模式。
- Nuxt、React、Svelte、Angular、Next、SvelteKit 和非前端技术栈不在此 skill 适配范围内。
